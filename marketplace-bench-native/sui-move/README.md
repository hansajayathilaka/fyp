# sui-move: the native-DAG leg (Sui / Move)

Status: **built and fully run end-to-end.** Real local Sui network, real Move package
published to it, real seeded fixtures, real benchmark CSVs for all four applicable
operations (`mint`, `list`, `buy`, `cancel`) — see [`RUNBOOK.md`](RUNBOOK.md) for exact
commands and [Results](#results-produced-this-run) below for what actually landed.

## Why Sui is the "purest" native-DAG leg of this comparison

Unlike `conflux-core` (a DAG ledger whose contract language is still Solidity, just
compiled for a different VM) and `hedera-native` (no smart-contract VM at all), Sui runs
its own contract language, **Move**, on an execution model built around a genuine DAG at
two levels:

- **Consensus**: Narwhal-Bullshark builds a DAG of certified transaction batches, not a
  chain of blocks.
- **Data model**: object ownership forms a causal DAG. Transactions touching disjoint
  owned objects have no ordering dependency and execute in parallel; only transactions
  that touch the same object (in particular, shared objects) need to be sequenced.

Nothing here goes through an EVM-compatibility shim. `mint`/`list`/`buy`/`cancel` are
direct Move function calls, submitted and measured through Sui's own JSON-RPC + the
official `@mysten/sui` TypeScript SDK.

## Local network: what was actually used

**No prebuilt `sui-test-validator` binary/image was needed or used** — that binary is
deprecated upstream. Its replacement, `sui start --force-regenesis --with-faucet`, ships
inside the official `mysten/sui-tools` Docker image, which *is* prebuilt (checked Docker
Hub first, per the task instructions; found `mysten/sui-tools:testnet`, `:mainnet`,
`:devnet` — all current, actively-pushed amd64 Linux images). No from-source `cargo build`
was needed at any point.

- **Image**: `mysten/sui-tools:testnet` (contains the `sui` CLI, version `1.78.0` at time
  of writing).
- **Command**: `sui start --force-regenesis --with-faucet --epoch-duration-ms=60000` (see
  `docker/docker-compose.yml`).
- **Ports** (Sui's own defaults, per `DESIGN.md`): `9000` JSON-RPC, `9123` faucet HTTP API,
  `9184` Prometheus metrics.
- **`--force-regenesis`**: fresh genesis (and fresh funded faucet) every container start —
  no persisted validator secrets, matching the "no `.env`/secrets" spirit of the existing
  `besuLocal`/`confluxLocal` tracks. This also means `dev-accounts.json`'s keypairs need
  re-funding (handled automatically by `common.ts`'s `loadOrCreateAccounts`) after a fresh
  `docker compose up` — same idea as `marketplace-bench`'s Conflux eSpace funding step.

## Operation mapping (per `../docs/DESIGN.md`)

| Solidity (`marketplace-bench`) | Sui / Move (this track) | Notes |
|---|---|---|
| `MarketplaceItem.mint` | `mpl_item::mint` | Move object create + transfer to sender |
| `IERC721.approve` | *(omitted)* | see below |
| `Marketplace.listItem` | `mpl_market::list` | wraps the item in a shared `Listing` object |
| `Marketplace.buyItem` | `mpl_market::buy` | atomic pay-with-`Coin<SUI>` + object transfer |
| `Marketplace.cancelListing` | `mpl_market::cancel` | reclaims the item, deletes the `Listing` |

### Why `approve` is omitted (not a gap — a category difference)

ERC-721's `approve`/`isApprovedForAll` exists because Solidity contracts have no built-in
notion of "the caller owns this value" — a *second* contract (the marketplace) needs
explicit permission to move a token it doesn't hold. Move's object model doesn't have
this problem: `mpl_market::list(item: MarketplaceItem, ...)` takes the item **by value**,
which only type-checks if the calling transaction's sender already owns that exact
object. Object ownership *is* the authorization; there is no allowance state to grant,
query, or revoke. This isn't a missing feature — it's one fewer transaction, and one
fewer class of bug (stale/over-broad approvals), that Sui's model makes structurally
impossible. `DESIGN.md` calls this out explicitly and instructs omitting it rather than
force-fitting a fake operation.

## Object model vs. account model — what changed in the contract logic

- **No `active` bookkeeping.** `Marketplace.sol`'s `Listing` struct carries an `active:
  bool` because the record persists in contract storage forever, even after being
  consumed — every `buyItem`/`cancelListing` call has to check it. A Sui `Listing` is a
  real object: `buy` and `cancel` both **destructure and delete** it
  (`mpl_market.move`). A double-buy or buy-after-cancel isn't a runtime check that could
  be forgotten — the object, and the only handle by which any function could reference
  it, no longer exists after the first successful call. See the module doc-comment in
  `contracts/marketplace/sources/mpl_market.move` for the full comparison.
- **No reentrancy guard needed** for the same reason `buyItem`'s `nonReentrant` modifier
  exists in Solidity: `buy` consumes (deletes) the shared `Listing` as its first act, so
  there is no listing state left for a reentrant call to observe or double-spend.
- **Token identity is the object ID**, not a separate integer `tokenId` counter read from
  contract storage. `mpl_item.move` keeps an `item_seq: u64` field purely for
  human-readable parity with the Solidity original's `tokenId` — it is never used to look
  anything up on-chain.
- **A shared `ItemCounter` object** stands in for Solidity's `_nextId` storage slot, since
  Move/Sui contracts have no global mutable statics — all state lives in objects.

## Scripts: how they work (TypeScript SDK + one deliberate CLI dependency)

`seed.ts` and `bench.ts` are pure `@mysten/sui` TypeScript SDK — no CLI, no Docker, direct
JSON-RPC. `deploy.ts` is a **hybrid**: compiling Move source into bytecode requires the
Move compiler, and there is no native `sui` binary for this host (Windows), so it shells
out to `docker run mysten/sui-tools:testnet sui move build --dump-bytecode-as-base64`
to get compiled module bytecode + dependency package IDs, then does the actual publish
**transaction** itself via `@mysten/sui`'s `Transaction.publish()`, signed by a locally
generated dev keypair. This mirrors `marketplace-bench/scripts/deploy.ts`'s own
dependency on a compiler toolchain (`hardhat compile` / `solc`) — every chain's deploy
step needs its native compiler; Sui's just isn't reachable as a plain npm dependency the
way solc is.

Env-var conventions mirror the reference harness as closely as Sui's model allows:

| Env var | Used by | Meaning |
|---|---|---|
| `BENCH_OPERATION` | bench.ts | `mint\|list\|buy\|cancel` (no `approve`) |
| `BENCH_BATCH_SIZE` | bench.ts | concurrent sends per repeat |
| `BENCH_REPEATS` | bench.ts | repeats; repeat 0 is `warmup=true`, excluded from analysis |
| `BENCH_TIMEOUT_MS` | bench.ts | default 60000, same as the reference harness |
| `BENCH_NODE_COUNT` | bench.ts | informational tag; this is the 1-validator baseline |
| `SEED_TOKEN_COUNT` / `SEED_LISTING_COUNT` | seed.ts | fixture pool sizes |
| `SEED_LISTING_PRICE_SUI` | seed.ts | listing price in SUI (converted to MIST) |
| `SEED_SELLER_COUNT` | seed.ts, bench.ts | size of the dev account pool (default 5 + 1 spare) |

No `.env` file, no secrets: `dev-accounts.json` holds freshly generated Ed25519 keypairs,
funded from the local faucet — devnet-only, worthless off this container, regenerated
(and re-funded) fresh whenever the network is force-regenesis'd.

## CSV schema mapping

| DESIGN.md column | Sui source |
|---|---|
| `chain` | `sui` |
| `architecture` | `dag` |
| `language` | `move` |
| `txId` | the transaction digest |
| `confirmUnit` | checkpoint sequence number (see below) |
| `feeUnitsUsed` | net MIST charged ÷ gas price (a derived unit count — Sui doesn't expose a raw "gas units" integer the way `gasUsed` does on EVM; see below) |
| `feeUnitPrice` | the transaction's gas price, in MIST/unit — explicitly set to the network's live reference gas price (`suix_getReferenceGasPrice`) before every send, never left as an implicit default |
| `feePaidNative` | net MIST charged: `computationCost + storageCost - storageRebate` |
| `feeCurrency` | `SUI` |

**`confirmUnit` timing note**: `submittedAt`/`receivedAt` bracket Sui's synchronous
execution response (`signAndExecuteTransaction` resolving with `effects` — the practical
confirmation signal, equivalent to what `bench.ts` waits for with `tx.wait()` on the EVM
side). Checkpoint *assignment*, however, happens asynchronously from execution on Sui —
so `bench.ts` does a short best-effort follow-up poll (up to 5 tries, 200ms apart) purely
to populate the `confirmUnit` column, and that poll is **not** counted in the
`submittedAt`→`receivedAt` timing window. In every run captured here it resolved on the
first or second attempt.

## Cost integrity — read before citing `feePaidNative` numbers

Per `DESIGN.md`'s non-negotiable #4 ("do not let this come out to zero by accident"):

- **The reference gas price on this local network is a real, non-zero `1000 MIST/unit`**
  (`suix_getReferenceGasPrice`), not a `min-gas-price=0` local-genesis artifact the way
  `besuLocal` is (see `../../marketplace-bench/RUNBOOK.md` §6). Every transaction here was
  sent at that live reference price, explicitly set via `tx.setGasPrice(...)` rather than
  left to an SDK default.
- **However, `feePaidNative` can legitimately be very small or even *negative* for
  operations that delete storage** — most visibly `cancel`, and to a lesser extent `buy`.
  Sui refunds ~99% of a storage deposit when the object it was paid for is deleted, and
  that deposit was paid by a *prior* transaction (the `mint`/`list` that created the
  object) — not the deleting transaction itself. A single `cancel` call in this run's data
  deletes four objects at once (the `Listing`, the reclaimed `MarketplaceItem`, and
  version bookkeeping), and the resulting rebate can exceed that transaction's own
  computation + new-storage cost. `netMistCharged()` in `scripts/common.ts` reports this
  **signed, unclamped** — a `cancel` row showing a small or negative `feePaidNative` is a
  real measurement of Sui's storage-rebate economics, not a broken zero-price genesis.
  Flooring it at 0 would have reproduced exactly the failure mode `DESIGN.md` warns about
  (a cost column that silently reads zero) while hiding the actual, more interesting
  finding — that deleting state on Sui can be a net *refund*, something that has no
  analogue in Solidity's cost model at all. Cite `cancel`'s cost numbers in the final
  report with this caveat attached, the same way `besuLocal`'s zero-gas-price caveat is
  attached in the reference `RUNBOOK.md`.
- `mint` (pure storage creation, no deletions) and `list`/`buy` (net creators, smaller
  rebates) all came out solidly positive in every run captured here — see
  [Results](#results-produced-this-run).

## Known gaps

- **`approve` is not implemented.** By design — see [above](#why-approve-is-omitted-not-a-gap--a-category-difference).
  Not a limitation encountered during the build; DESIGN.md instructs omitting it.
- **`feeUnitsUsed` is a derived value, not a raw on-chain field.** Sui's gas accounting
  bills `computationCost`/`storageCost`/`storageRebate` directly in MIST, not as a
  units-times-price product the way EVM's `gasUsed`/`gasPrice` pair is defined. There is
  no single on-chain integer that plays exactly `gasUsed`'s role. `feeUnitsUsed` here is
  `netMistCharged / gasPrice` — a normalized "how many reference-gas-price-equivalent
  units did this cost" figure, documented so it isn't mistaken for a raw protocol field.
- **This is the 1-validator local-network baseline**, same scope disclaimer as
  `besuLocal`/`confluxLocal`'s single-node setups in the reference track — no
  node-count-sensitivity data was collected here.
- **No `priceTier`/fee-market sensitivity sweep.** Sui's reference gas price is a
  network-wide epoch parameter, not a per-transaction knob the sender picks the way EVM's
  `maxFeePerGas` is — a sender can only pay *more* than the reference price to prioritize
  congested shared-object access, which doesn't apply to this benchmark's fixture-per-tx
  design (no two concurrent jobs contend for the same object). `priceTier` is left empty
  in every row, per `DESIGN.md`.
